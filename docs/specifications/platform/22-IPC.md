# P22 — IPC de baja latencia
Fuentes: [D-Bus spec](https://dbus.freedesktop.org/doc/dbus-specification.html), [zbus](https://docs.rs/zbus/latest/zbus/), [Wayland architecture](https://wayland.freedesktop.org/docs/book/Architecture.html), [RemoteDesktop portal](https://flatpak.github.io/xdg-desktop-portal/docs/doc-org.freedesktop.portal.RemoteDesktop.html).
## Diseño
D-Bus/zbus para control y servicios estándar, Wayland para superficies/input, PipeWire/DMABUF para datos gráficos cuando autorizados; no enviar frames por JSON/D-Bus. FD passing negociado por transporte y verificado por recurso. CLI/MCP adaptan acciones tipadas, no segunda autoridad. Para tráfico interno muy frecuente medir primero D-Bus; socket Unix privado y mensajes versionados solo si perfil muestra cuello de botella. No crear protocolo binario general por anticipado. Credenciales de peer/bus verificadas, scopes, permisos por invocación, no confiar ID suministrado por cliente. Transporte local no es autorización. Acotar tamaños, frecuencia, cola, timeout, errores y validación de schema. Suscripción filtered con sequence + snapshot; revocación corta nuevas acciones y sesiones autorizadas según contrato.
Evaluar round-trip p50/p95/p99, saturación, CPU, allocation, tamaño payload 64B/1KiB/64KiB, 1/10/50 clientes, overhead serialización y broker. Objetivos iniciales candidatos: control local p95 <5ms en idle y <20ms carga definida (excluye operación dominio/confirmación), revisar según hardware; no benchmark real. Evitar polling; batches solo cuando preservan latencia y semántica. P22a: ping/snapshot sintético; b: flujo eventos y backpressure; c: restart/version mismatch/cancel; d: autorización y FD scopes en fixtures; e: comparar transports bajo carga, justificar si nuevo.
