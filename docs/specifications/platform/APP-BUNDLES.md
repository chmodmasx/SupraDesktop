# A00 — Applications / SupraBundle
Estado: PROPOSED; consulta documental, no implementación. Objetivo: experiencia Finder de arrastrar, instalar, abrir, mover y quitar aplicaciones, sin nuevo gestor de paquetes obligatorio.
Fuentes: [Apple About Bundles](https://developer.apple.com/library/archive/documentation/CoreFoundation/Conceptual/CFBundles/AboutBundles/AboutBundles.html), [AppDir](https://docs.appimage.org/reference/appdir.html), [AppImage integration](https://docs.appimage.org/reference/desktop-integration.html), [AppImageLauncher](https://github.com/TheAssassin/AppImageLauncher), [helloSystem bundles](https://hellosystem.github.io/docs/developer/application-bundles), [Flatpak basic concepts](https://docs.flatpak.org/en/latest/basic-concepts.html), [Flatpak conventions](https://docs.flatpak.org/en/latest/conventions.html), [Desktop Entry](https://specifications.freedesktop.org/desktop-entry/latest-single/).
## Decisión recomendada
Primero implementar vista Applications y soporte AppImage/AppDir. Después, si una necesidad comprobada lo justifica, añadir extensión opcional SupraBundle (.app provisional, no compatible con binarios macOS). No crear repositorio de paquetes, formato comprimido, runtime ni resolver dependencias propios en M00. El formato no determina estética: SupraUI, tokens y pruebas sí. Las apps nativas pueden distribuirse también como Flatpak, AppImage o paquete Arch de base. No exigir formato nativo.
## Vista y operaciones
~/Applications directorio real para portables; nombre mostrado localizado, ubicación configurable, no asumir ruta XDG estándar de Applications. Vista virtual supra://applications reúne registros del sistema y usuario: .desktop, Flatpak exports, bundles y AppImage. No ofrecer instalación .deb en la distribución oficial; mostrar explicación y alternativas compatibles. Los paquetes Arch de base aparecen como gestionados por la imagen, no como portables. Evitar duplicados por identidad de instalación (proveedor, ID, scope, versión, ubicación); distinguir duplicados intencionales. AppRegistry es autoridad; Files, Dock, Search y Settings son clientes.
Drop AppImage: copiar a staging, confirmar integración si es necesaria, inspeccionar metadatos sin ejecutar binario, registrar launcher e icono validados, marcar permiso de ejecución únicamente tras aceptación, commit atómico y reindexación. AppDir o .app: copiar directorio completo y validar estructura. Abrir aplicación requiere acción explícita. flatpak/ref: delegar instalación a Flatpak y mostrar origen, runtime y permisos. No ejecutar scripts de paquete fuera del gestor. Mover a papelera o quitar portable -> retirar registro; desinstalar paquete -> gestor correspondiente y consentimiento, nunca rm sobre archivos administrados. Mantener datos/config por defecto. Si la app está en ejecución avisar y no sustituir archivos usados sin estrategia de versión.
## Propuesta de contrato futuro
AppDir compatible (AppRun, un desktop entry raíz, icono y .DirIcon, usr/bin, usr/lib, usr/share), supra-app.json opcional con schemaVersion, reverse-DNS id, version, arch, runtime constraints, capabilities/actions schema, menu support, restore schema, provenance/update source, licenses. No usar metadata para conceder permisos ni afirmar firma/autenticidad. ID declarado no prueba identidad. No interpretar comandos de manifiesto durante descubrimiento, limitar extracción y validar rutas, symlinks y recursos. Un .app de macOS no es ejecutable Linux; comprobar formato/arquitectura. No copiar recursos Apple. Licencias de upstream obligatorias. Firma y hashes distinguen integridad de confianza; paquetes sin firma no se ejecutan automáticamente. AppImage no es sandbox. Preferir Flatpak cuando se requiera aislamiento, con permisos revisados; no prometer aislamiento de bundles sin mecanismo comprobado.
## Actualización
Backend propietario por formato; Flatpak conserva sus transacciones y updates; la base Arch se actualiza por despliegue completo. AppImage usa metadatos de actualización cuando soportados, nunca inventar disponibilidad; para bundle considerar reemplazo versionado y rollback con consentimiento, no actualizador propio hasta necesidad. No ejecutar postinstall de portables automáticamente. App data XDG separado, no guardar documentos dentro del bundle por defecto.
## Pruebas A00
a: drag/drop portable, launch explícito, registro en Dock/Search y remove; b: Flatpak delegado, AUR encapsulado y cancelación, nunca borrar archivos gestionados; c: duplicados, rutas localizadas, cambios externos, rename, desconexión de volumen, noexec, FUSE ausente, arquitectura incorrecta; d: metadatos inválidos y archivos no confiables (fixtures inocuos), permisos, rollback, fallo parcial, disco lleno, sin autoejecución; e: aplicación nativa distribuida en dos formatos, misma identidad visual y acciones, documentación de diferencias; f: coexistencia con Plasma, eliminación de integración sin borrar datos. No prometer compatibilidad universal. La decisión de crear formato definitivo queda tras demostrar limitaciones de AppDir/AppImage/Flatpak.

## Aclaración de plataforma
Vista Applications aceptada por el mantenedor. La distribución oficial candidata no incluye APT/dpkg ni proveedor .deb. AppRegistry agrega Flatpak, AppImage/AppDir, bundles opcionales, aplicaciones de contenedor exportadas y aplicaciones de base. Borrar una entrada de base no elimina archivos del sistema: indicar que pertenece a la imagen y ofrecer únicamente mecanismos soportados. Extensiones del kernel se administran fuera de Applications.
