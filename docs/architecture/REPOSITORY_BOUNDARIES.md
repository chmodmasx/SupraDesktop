# Fronteras de repositorios y releases
Estado PROPOSED. El mantenedor ya aprobó independencia entre escritorio y distribución; la separación física en repositorios es recomendación, no repositorio creado. SupraOS es nombre provisional, pendiente de comprobar disponibilidad y aprobación. No migrar SupraLINUX existente.
## Dos monorepos
SupraDesktop: compositor, glass, UI, apps, shell, acciones/AI Ready, tokens, SDK, protocolos, laboratorios, pruebas y empaquetado portable del escritorio.
Distribución oficial: imágenes Arch, snapshot locks, PKGBUILD de integración, SupraDeploy/SupraLayers, adaptador Arkdep y parches, ISO, Calamares, recovery, claves públicas, manifests, pruebas VM/hardware y pipeline de releases. Nunca claves privadas en Git.
## Dependencias
Distro consume commit/tag/artefacto identificado de SupraDesktop y sus tokens, SDK y esquemas publicados, no código duplicado ni ramas flotantes. Escritorio consume APIs Linux y contratos de proveedores; puede ejecutarse en otras distribuciones, sin dependencia runtime de SupraDeploy. Adaptador de actualización de sistema opcional, negociado por versión/capabilities. Ambos repos pueden usar mismos principios con referencia canónica y revisión explícita; evitar copiar documentos y divergencias. CI del escritorio prueba sin distro; CI distro prueba integración de release fijada. Un cambio en contrato requiere compatibilidad y test cruzado. La integración de claves, compilación y publicación de imágenes no debe elevar permisos de CI del escritorio.
## Migración de documentación
Hasta que exista repo de distribución aprobado, docs/distribution y directorios reservados permanecen aquí. Después transferir historia relevante, ADRs y especificaciones conservando trazabilidad, actualizar enlaces y sustituir duplicados por referencia canónica; no eliminar fuentes ni fusionar main automáticamente. No crear tercer repo de SDK/tokens hasta necesidad real. No crear forks remotos sin autorización; incorporar código auditado por manifiesto y parches.
